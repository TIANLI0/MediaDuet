# MediaDuet Link Protocol — Version 1

Status: **implemented** by `windows/core` (C++) and `android/app` (Kotlin).
Normative test vectors: [`test-vectors/`](test-vectors/) (generated by
[`tools/gen_vectors.py`](tools/gen_vectors.py) using the independent Python
`cryptography` package). Both implementations run these vectors in their unit tests.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

---

## 1. Roles and transports

| Role | Platform (v1) | Responsibility |
|------|---------------|----------------|
| **Server (S)** | Android | Listens on Bluetooth RFCOMM and TCP; accepts connections; answers handshakes. |
| **Client (C)** | Windows | Discovers, connects, chooses the primary transport, reconnects with back-off. |

Rationale: Android background execution limits make an always-listening server
inside an already system-bound process (NotificationListenerService) cheaper than
an outgoing reconnect loop. Windows has no such limits, and since Windows only
makes *outgoing* connections no inbound firewall rule is needed.

Roles only affect connection setup. After the handshake the protocol is fully
symmetric: either side may send any message type permitted by §6.

Two Android devices can also be linked; one of them then takes the client role
(§13).

### 1.1 Bluetooth Classic RFCOMM

* Service UUID: `5f3a8c2e-7d41-4b9a-9c61-2e8d0f6b4a17`
* SDP service name: `MediaDuet`
* Android uses `listenUsingRfcommWithServiceRecord` (secure, requires a bonded link).
  Windows uses `RfcommDeviceService` + `StreamSocket` with
  `SocketProtectionLevel::BluetoothEncryptionAllowNullAuthentication` or stronger.
* BLE is **not** used for data.

### 1.2 TCP (LAN)

* DNS-SD service type: `_mediaduet._tcp`, domain `local`.
* TXT record: `v=1`, `id=<deviceId>` (§3.1), `n=<urlencoded device name, ≤ 40 bytes>`,
  `p=android` (optional: the advertiser's platform).
* Default port **47321**; if busy the server binds an ephemeral port and advertises it.
* Manual connection uses `host:port` entered by the user (default port 47321).
* LAN traffic is always encrypted (§5). TLS is not used; see §4.4 for the rationale.

A logical **link session** (§7) can span several transport connections.

## 2. Framing

Every transport carries a byte stream of frames:

```
+----------------+-----------+---------------------+
| length (u32 BE)| type (u8) | body (length-1 B)   |
+----------------+-----------+---------------------+
```

* `length` counts the type byte plus the body. `1 ≤ length ≤ 262 144` (256 KiB).
  A frame exceeding the limit MUST cause the connection to be closed.
* `type`:

| Value | Name | Body | Allowed |
|-------|------|------|---------|
| `0x01` | HANDSHAKE | UTF-8 JSON envelope (§6), ≤ 16 KiB | before the session keys exist |
| `0x02` | SECURE | AES-256-GCM record (§5) | after the handshake only |

Any other type, a HANDSHAKE frame after keys exist, or a SECURE frame before keys
exist MUST close the connection.

### 2.1 Secure record plaintext

```
+-------------+-------------------------+
| channel (u8)| data                    |
+-------------+-------------------------+
```

| Channel | Name | Data | Limit |
|---------|------|------|-------|
| `0x01` | CONTROL | UTF-8 JSON envelope (§6) | 64 KiB |
| `0x02` | BLOB | binary chunk (§8.2) | 32 KiB + 40-byte header |

Senders SHOULD prioritise CONTROL records over queued BLOB records so that large
artwork transfers never delay playback commands.

## 3. Identity and pairing

### 3.1 Device identity

* `deviceId`: 16 random bytes from a CSPRNG, lowercase hex (32 chars). Generated once.
* `deviceName`: user visible, ≤ 64 UTF-8 chars.
* Long-term secret per peer: `K` (32 bytes) established by pairing (§3.3).
  Stored with platform secure storage (Windows DPAPI, Android Keystore wrapped).

### 3.2 Primitives

| Purpose | Primitive |
|---------|-----------|
| Key agreement | ECDH over NIST P-256; shared secret = 32-byte big-endian X coordinate |
| Public key encoding | SEC1 uncompressed point, 65 bytes (`0x04‖X‖Y`), base64 (RFC 4648, padded) in JSON |
| Hash | SHA-256 |
| MAC | HMAC-SHA-256 |
| KDF | HKDF-SHA-256 (RFC 5869) |
| AEAD | AES-256-GCM, 12-byte nonce, 16-byte tag |
| Randomness | Windows `BCryptGenRandom`, Android `SecureRandom` |

No custom primitives are used. Binary fields in JSON are base64.

### 3.3 Pairing (first contact)

Pairing is only accepted by S while the user has opened **pairing mode** in the
Android app (time-limited, 5 minutes). Outside pairing mode S answers
`pair.request` with `pair.result {ok:false, reason:"pairing_disabled"}` and closes.

```
C → S  HANDSHAKE pair.request  {device, epk: epk_C, nonce: n_C}
S → C  HANDSHAKE pair.response {device, epk: epk_S, nonce: n_S}
       -- both compute Z, TH, SAS; both show the 6-digit SAS; users compare --
C → S  HANDSHAKE pair.confirm  {mac: HMAC(K, "confirm" ‖ "C" ‖ TH)}   (after local user accepts)
S → C  HANDSHAKE pair.confirm  {mac: HMAC(K, "confirm" ‖ "S" ‖ TH)}   (after local user accepts)
       -- each side verifies the peer MAC, then stores K --
S → C  HANDSHAKE pair.result   {ok: true}
       -- connection is closed; the client reconnects with §4 --
```

Either side may send `pair.result {ok:false, reason}` at any time to abort (`"rejected"`,
`"timeout"`, `"mac_mismatch"`, `"pairing_disabled"`, `"busy"`). The whole exchange
MUST complete within 120 s.

Definitions (`‖` = byte concatenation; all fields fixed length):

```
n_C, n_S   : 32 random bytes each
epk_C/S    : 65-byte uncompressed P-256 points (fresh per attempt)
id_C, id_S : the 32 ASCII bytes of each deviceId
Z          : ECDH(esk_C, epk_S) = ECDH(esk_S, epk_C)        (32 bytes)
TH         : SHA-256("MediaDuet-pair-v1" ‖ n_C ‖ n_S ‖ epk_C ‖ epk_S ‖ id_C ‖ id_S)
PRK        : HKDF-Extract(salt = TH, IKM = Z)
SAS        : (u32_be(HKDF-Expand(PRK, "sas", 4)) mod 1 000 000), zero-padded to 6 digits
K          : HKDF-Expand(PRK, "pairing key", 32)
```

The SAS comparison gives MITM protection with probability 1 − 10⁻⁶ per attempt
(the same idea as Bluetooth Secure Simple Pairing "numeric comparison").
On Bluetooth the link is additionally encrypted and authenticated by the system
bond; the application layer never trusts the Bluetooth bond alone.

### 3.4 Revocation

A device that removes a peer deletes `K`. The next `hello` from that peer receives
`error {code:"not_paired"}` and the connection is closed. A peer that receives
`not_paired` MUST mark the pairing as revoked and stop reconnecting.

## 4. Session handshake (paired devices)

```
C → S  HANDSHAKE hello      {device, protocol:{min,max}, caps, epk: epk_C, nonce: n_C,
                             transport: "bt"|"lan", resume?: sid}
S → C  HANDSHAKE hello.ack  {device, protocol: v, caps, epk: epk_S, nonce: n_S,
                             sid, resumed: bool, mac: HMAC(K, "server" ‖ TH)}
C → S  HANDSHAKE auth       {mac: HMAC(K, "client" ‖ TH)}
       -- from here on only SECURE frames --
S → C  SECURE    session.ready {sid}
```

```
TH        = SHA-256("MediaDuet-session-v1" ‖ n_C ‖ n_S ‖ epk_C ‖ epk_S ‖ id_C ‖ id_S)
Z         = ECDH(esk_C, epk_S)
PRK       = HKDF-Extract(salt = K, IKM = Z)
key_c2s   = HKDF-Expand(PRK, "c2s key" ‖ TH, 32)
key_s2c   = HKDF-Expand(PRK, "s2c key" ‖ TH, 32)
iv_c2s    = HKDF-Expand(PRK, "c2s iv"  ‖ TH, 4)
iv_s2c    = HKDF-Expand(PRK, "s2c iv"  ‖ TH, 4)
```

* S looks up `K` by `hello.src`. Unknown → `error {code:"not_paired"}` + close.
* Version: S picks the highest version in `[min,max] ∩ supported`. None →
  `error {code:"version_unsupported"}` + close.
* C MUST verify `hello.ack.mac` before sending `auth`; S MUST verify `auth.mac`
  before accepting any SECURE frame. MACs are compared in constant time.
* Mismatch → `error {code:"auth_failed"}` + close. Handshake timeout: 10 s.
* Fresh ephemeral keys per connection give forward secrecy; the MAC over `TH`
  binds the ephemeral keys to `K`, so an attacker without `K` cannot complete
  either side. Replaying an old `hello` fails because `n_S` is fresh.

### 4.4 Why not TLS?

Both platforms ship TLS, but pinning self-signed certificates across Schannel and
Conscrypt and running TLS over RFCOMM streams adds substantial code and failure
modes. The construction above is the TLS 1.3 PSK-DHE pattern (PSK as HKDF salt,
fresh ECDHE, transcript-bound keys) built only from platform primitives. It is
documented here and covered by cross-implementation test vectors.

## 5. Record protection

* Each direction has its own key, a 4-byte IV prefix and a 64-bit sequence number
  starting at 0, incremented per record.
* `nonce = iv_dir ‖ u64_be(seq)` (12 bytes).
* `AAD = "MDv1" ‖ 0x02` (5 bytes).
* Frame body = `ciphertext ‖ tag(16)`.
* Decryption failure (including a replayed, reordered or dropped record) MUST
  close the connection. The sequence number MUST NOT wrap (close at 2⁶³).

## 6. Envelope

All JSON messages (handshake and control) share one envelope:

```json
{
  "v": 1,
  "type": "media.command",
  "id": 42,
  "ts": 1760000000000,
  "src": "4f1c…(32 hex)",
  "sid": "9a0b…(32 hex) or empty during handshake",
  "re": 41,
  "body": { }
}
```

| Field | Type | Rules |
|-------|------|-------|
| `v` | int | Protocol major version. Must equal the negotiated version (handshake: `1`). |
| `type` | string | ≤ 48 chars, `[a-z0-9.\-]`. Unknown types → ignored (forward compatibility), except during the handshake where they abort. |
| `id` | int | Per sender, per link session, strictly increasing, 1 … 2⁵³−1. |
| `ts` | int | Sender wall clock (ms since epoch). Informational only; never used for security decisions. |
| `src` | string | Sender `deviceId`. Must equal the authenticated peer id. |
| `sid` | string | Link session id; `""` during the handshake. |
| `re` | int | Optional: `id` of the message this one answers. |
| `body` | object | Type specific. Unknown fields MUST be ignored. |

Receivers MUST validate types and limits and drop messages that violate them
(sending `error {code:"bad_message", re}` where possible).

### 6.1 Common string limits

| Field | Max UTF-8 code points |
|-------|------------------------|
| device name | 64 |
| title / artist / album / album artist | 512 |
| app name | 128 |
| app id / package / AUMID | 256 |
| session key | 300 |
| error message | 512 |

Over-long strings are truncated by the sender and rejected by the receiver.

### 6.2 `DeviceInfo`

```json
{"id":"…","name":"Tianli's PC","platform":"windows","model":"…","os":"10.0.26340","app":"1.0.0"}
```
`platform` ∈ `windows`, `android`.

## 7. Link session, de-duplication and transport switching

* A **link session** (`sid`, 16 random bytes hex, chosen by S) represents the
  logical connection between two paired devices. It survives transport switches.
* C sends `resume: <sid>` in `hello` when it still has a session. S accepts
  (`resumed: true`) if that session exists and was last active < 10 minutes ago;
  otherwise S creates a new `sid` and replies `resumed: false`.
* Several transport connections may be attached to one session at the same time
  (e.g. RFCOMM + TCP). Message ids are per session, not per transport.
* **Receiver de-duplication**: each side remembers, per session, the highest
  peer id seen and the set of the last 1024 peer ids. A duplicate is not
  re-processed; if it is a `media.command` the cached `media.command.result`
  is re-sent instead.
* **Primary transport**: C designates the primary by sending `link.primary {}`
  over it. S sends unsolicited messages on the most recently designated primary;
  replies go back on the transport the request came from.
* **Re-sending**: when a transport dies, C re-sends un-answered `media.command`
  messages (same `id`) on the new primary *only* if the session was resumed and
  the command is younger than 5 s; otherwise they fail with `link_lost`. Thanks
  to de-duplication, a command is executed at most once even if two transports
  delivered it.
* If `resumed:false`, both sides discard session state (pending commands fail,
  peer media state is cleared and re-sent by `media.snapshot`).

### 8.3 `MediaSnapshot`

Sent whenever the sender's local media state changes meaningfully (status,
track, active session, capabilities, artwork, seek). It is a full snapshot and
therefore idempotent. Senders MUST suppress snapshots that are equal to the
previous one apart from the naturally advancing position. Progress is never
streamed: receivers extrapolate from `positionMs` using a monotonic clock.

```json
{
  "gen": 17,
  "at": 86400123,
  "active": "com.netease.cloudmusic#1",
  "sessions": [
    {
      "key": "com.netease.cloudmusic#1",
      "app": {"id": "com.netease.cloudmusic", "name": "网易云音乐"},
      "title": "…", "artist": "…", "album": "…", "albumArtist": "…",
      "trackId": "c0ffee…(16 hex)",
      "durationMs": 245000,
      "positionMs": 12345,
      "rate": 1.0,
      "status": "playing",
      "actions": ["play","pause","next","previous","seek"],
      "artwork": {"hash": "<sha256 hex>", "mime": "image/jpeg", "size": 34512},
      "kind": "music",
      "volume": {"level": 0.8, "muted": false},
      "outputLatencyMs": 180,
      "customActions": [{"id": "like", "title": "喜欢", "icon": {"hash": "<sha256 hex>", "mime": "image/png", "size": 812}}],
      "queue": {"count": 37, "rev": "5f0c2a91", "activeId": 12}
    }
  ]
}
```

* `gen`: per-sender counter, incremented for every snapshot; receivers ignore
  snapshots with a `gen` not greater than the last applied one in this session.
* `status` ∈ `playing`, `paused`, `stopped`, `buffering`, `unknown`.
* `actions` ⊆ `play`, `pause`, `toggle`, `next`, `previous`, `seek`, `stop`.
* `at` (optional, integer ≥ 0): the sender's monotonic clock (the one in
  `ping.t`) at which every `positionMs` of the snapshot holds. Receivers with a
  clock estimate (§11.1) anchor the positions at `at` converted to their own
  clock, so neither the snapshot's own transit time nor queueing on the link
  shifts them. Without `at` or an estimate, `positionMs` is the sender's
  estimate *at send time* and receivers add `rtt/2` when known.
  `durationMs`/`positionMs` may be `null`.
* `trackId` = first 16 hex chars of SHA-256(`title` ‖ 0x1F ‖ `artist` ‖ 0x1F ‖
  `album` ‖ 0x1F ‖ decimal((`durationMs` + 500) div 1000), or "" when unknown),
  over UTF-8. Changes reset lyric timelines.
* `kind` ∈ `music`, `video`, `other`.
* `volume` (optional): the app's own volume (Windows per-app mixer) when the sender can control it.
* `outputLatencyMs` (optional, integer 0–2000): estimated delay between the
  reported `positionMs` and the sound being audible on the device that plays
  the session, e.g. ≈ 150–250 ms for Bluetooth headphones, 0 for wired /
  built-in outputs. Senders omit it (or send 0) when unknown and update it when
  the output changes (it counts as a meaningful change). Receivers treat a
  missing, non-numeric or out-of-range value as unknown (0) and use it to delay
  lyrics for that session (display position = position − outputLatencyMs −
  the user's per-app offset); playback control is unaffected.
* `customActions` (optional, ≤ 8): the player's own buttons (Android
  `PlaybackState.CustomAction`: like / favourite, shuffle, repeat …) with `id`
  (≤ 128), `title` (≤ 64) and an optional `icon`: a small PNG with alpha
  addressed like artwork (`artwork.get`); receivers tint it. Pressed with
  `media.command {action:"custom", customAction:id}`. Receivers skip malformed
  entries.
* `queue` (optional): the player exposes a play queue of `count` entries;
  `activeId` is the current entry. Receivers fetch it with `media.queue.get
  {key}` whenever `rev` changes (a change of `activeId` alone needs no fetch).
* `ids` (optional): the current track's ids in music catalogues when the player
  exposes them — `netease` (decimal song id), `qqmusic` (songmid), `spotify`
  (track id), each 1–64 ASCII letters / digits; receivers drop invalid entries.
  Used by handoff (§8.7) to open the exact song instead of searching for it.
* At most 16 sessions; senders exclude their *own* bridged mirror sessions
  (e.g. MediaDuet's SMTC bridge on Windows), which prevents echo loops.

### 8.4 `MediaCommand`

```json
{"key": "spotify.exe", "action": "seek", "positionMs": 60000,
 "origin": "user", "reason": "ui"}
```

* `key` `null` → the receiver's active session.
* `action` ∈ the session's `actions`, plus `custom` (with `customAction`, an id
  from `customActions`) and `playQueueItem` (with `queueId`, an entry `id` from
  `media.queue`); those two are never listed in `actions`.
* `origin` ∈ `user` (a person pressed a button), `policy` (the arbitration
  engine). Receivers record the origin so that state changes caused by policy
  are not mistaken for user actions (§10).
* The receiver checks `actions` support before executing; unsupported →
  `media.command.result {ok:false, error:{code:"action_unsupported"}}`.
* Result timeout on the sender: 5 s.

### 8.5 `PolicyStatus`

```json
{"mode":"windows_first","enabled":true,
 "remote":"policy_paused","local":"playing",
 "lastAction":{"what":"pause_remote","reason":"windows_audio_active","app":"chrome.exe","at":1760000000000}}
```

`mode` ∈ `off`, `windows_first`, `android_first`, `latest`, `custom`.

### 8.6 Artwork BLOB chunks

```
+-----------------+----------------+-----------------+----------------+
| sha256 (32 B)   | total (u32 BE) | offset (u32 BE) | bytes (≤32 KiB)|
+-----------------+----------------+-----------------+----------------+
```

* Total artwork size ≤ 1 MiB; senders downscale to ≤ 512×512 JPEG first.
* Receivers reassemble, verify SHA-256, and cache by hash (content addressed,
  so each image is fetched and decoded at most once).
* A receiver requests artwork only for hashes it does not have cached.

### 8.7 Handoff (cap `handoff`)

"Continue on the other device": the song a session plays on one device continues
in a music app on the other, at the same position, and the source pauses.

* App ids: `netease` (NetEase Cloud Music), `qqmusic` (QQ Music), `spotify`.
  A session belongs to one by its app id: contains `cloudmusic`, `qqmusic`,
  `spotify` (case-insensitive; Windows exe / AUMID or Android package).
* The **PC coordinates both directions** (it is the arbitration authority, §10).
  The phone's UI sends `handoff.start`; the PC's UI talks to its host directly.
* The coordinator picks the app: the one asked for if the target device has it,
  else the source's own app if it has that, else its first app; none →
  `app_unavailable`.
* Phone as the target: the PC sends `handoff.play`; the phone resolves the song
  (`ids` of the source session, else a catalogue lookup by title / artist /
  album / duration with the lyrics matching rules), opens it and answers
  `handoff.result {ok:true, state:"playing", key}` once session `key` of that
  app shows the song (titles equal after normalisation or one a prefix of the
  other, durations within 5 s) and plays, within 20 s. A paused target that
  shows the song is started after 2.5 s. When the phone may not open the app
  from the background it posts a notification, sends `handoff.progress
  {state:"tap_to_continue"}` and waits up to 90 s for the tap.
* PC as the target: the same, inside the host (NetEase `orpheus://` web command,
  QQ Music `QQMusic.exe /tencentprotocol`, Spotify `spotify:` URIs), 25 s.
* `state:"opened"`: the app shows the song (or, without a catalogue id, a search
  for it) but playback could not be confirmed; the source keeps playing.
* On `playing` the coordinator pauses the source (a *user* pause: arbitration
  never resumes it, §10) and, from 3 s into the song, seeks the target to the
  source's live position (+ half the RTT for the phone).
* `handoff.start` is answered with an outcome:
  `{ok, state?, error?:{code}, to:"pc"|"phone", app, title}`, within 120 s.
* Error codes: `app_unavailable`, `not_found` (not in that app's catalogue),
  `network` (the catalogue lookup failed), `launch_failed`, `timeout`,
  `no_session` (the source is gone), `busy` (one handoff at a time),
  `link_lost`, `unsupported`.
* Only the PC coordinates: a phone receiving `handoff.start`, or a PC receiving
  `handoff.play`, answers `handoff.result {ok:false, error:{code:"unsupported"}}`.

## 9. Audio streaming (experimental)

Control-plane only; audio never travels over RFCOMM.

`AudioOffer`:
```json
{"streamId":"…","direction":"windows_to_android","codec":"pcm_s16le",
 "sampleRate":48000,"channels":2,"frameMs":10,"transport":"tcp"}
```
`streamId` is 16 random bytes, hex encoded (32 chars).

The receiver answers with `audio.answer {ok, port}` and opens a TCP listener on
that port (LAN only; never over RFCOMM). The sender connects and first sends the
16 raw `streamId` bytes, then frames as in §2 with type `0x03` (`AUDIO`). Each
frame body is an AES-256-GCM record (§5 rules: own sequence counter from 0)
using

```
base      = the session key of the direction audio-sender → audio-receiver, taken from
            the transport connection on which the audio.offer was sent/received
            (e.g. key_c2s of that connection when Windows streams to Android)
audio_key = HMAC-SHA-256(base, "audio key" ‖ streamIdBytes)          (32 bytes)
audio_iv  = HMAC-SHA-256(base, "audio iv"  ‖ streamIdBytes)[0..4)    (4 bytes)
AAD       = "MDv1" ‖ 0x03
```

Each record's plaintext is `u64_be(senderMonotonicMicros) ‖ PCM s16le interleaved`.

## 10. Arbitration semantics (informative; normative for the Windows engine)

Between a PC and a phone the arbitration engine runs on the **client (Windows)**
only, to avoid two engines fighting. Android reports state and executes commands;
it can request a mode change with `policy.config`. See `docs/architecture.md`
§Arbitration. Android devices arbitrate among themselves differently (§13.2).

Key rules that the protocol supports:

1. Commands sent by the engine carry `origin:"policy"`; the engine records a
   pending expectation and attributes the following `paused` snapshot to policy
   (`POLICY_PAUSED`) instead of the user.
2. A pause that the engine did not cause is `USER_PAUSED` and is never
   auto-resumed.
3. Snapshot echoes (the peer reporting a state the engine caused) never trigger
   a new arbitration decision.

## 11. Heartbeat and liveness

* `ping` every 15 s on the primary while any media is playing on either side,
  every 60 s otherwise; every 120 s on secondary transports.
* A transport with no inbound record for 3 × interval + 5 s is considered dead.
* Transport-level errors (socket closed, RFCOMM link loss) are handled
  immediately; heartbeats only cover silent failures.

### 11.1 Clock estimate

Both sides estimate the peer's monotonic clock from their own pings, NTP
style. A ping sent at `t0` (own clock) answered with `rt` (peer clock) and
received at `t1` gives `offset = rt − (t0 + t1) / 2`, wrong by at most
`(t1 − t0) / 2`.

* Keep up to 16 samples of the last 10 minutes. The estimate is the sample with
  the smallest error bound `rtt / 2 + age × 100 ppm` (clock drift), so slow or
  asymmetric round trips (Wi-Fi power save, Bluetooth sniff mode, a ping queued
  behind a BLOB) never move it.
* A sample further from the estimate than both half-RTTs plus 1 s means a clock
  restarted: drop the older samples. A new link session starts empty.
* For a quick estimate, send 5 extra pings 600 ms apart on a transport when it
  becomes the primary and when media starts playing on either side. They are
  not heartbeats (liveness keeps the intervals above).
* Snapshot anchor = `at − offset`, at most "now". An anchor more than 10 s in
  the past is not trusted; the receiver then falls back to "now − rtt/2".
* Peers that do not send `rt` or `at` keep working with the `rtt/2` estimate.

## 12. Versioning and extension

* Minor additions (new message types, new optional fields) do not change `v`.
* New capabilities are announced in `caps`; a sender MUST NOT send a message that
  depends on a capability the peer did not announce.
* v1 capability strings: `media.source`, `media.control`, `artwork`, `lyrics`,
  `policy.host`, `policy.client`, `audio.a2dp_sink`, `audio.recv.pcm`,
  `audio.send.pcm`, `smtc.bridge`, `notif.bridge`, `volume`, `handoff`,

## 13. Android ↔ Android

### 13.1 Linking

* Any Android device may connect to another one as the **client** (§1): it finds
  it with DNS-SD (§1.2) and connects over TCP; Bluetooth RFCOMM is not used
  between Android devices.
* Pairing (§3.3) is started by the user on either device; that device is the
  client, the other one must have its pairing window open. Both show the SAS.
* After pairing, of two Android devices **the one with the smaller `deviceId`**
  (lexicographic) dials and reconnects (back-off 2 s → 60 s, ±20 %); the other
  only listens. This keeps one link session per pair.
* The client sends `link.primary {}` on its connection; the server sends
  `session.ready` and `transport.info` as usual. The client keeps the reported
  LAN endpoints to find the server again.
* A device may hold sessions with a PC and several Android devices at once. The
  player shows one of them at a time; handoff and the PC audio receiver are PC
  features and are only offered for a connected PC.

### 13.2 Arbitration (`policy.peer`)

Every Android device runs its own engine but **only pauses and resumes its own
media sessions**; no device sends `media.command {origin:"policy"}` to another
Android device. Since no session has two controllers, engines cannot fight.

`PeerPolicy`:

```json
{"mode":"latest","priority":1,"call":false,"playing":true,"cause":"user",
 "onsetAt":1760000000000,"pausedAt":0,"app":"com.netease.cloudmusic"}
```

| Field | Meaning |
|-------|---------|
| `mode` | `off`, `latest` (the newest user-started playback wins), `priority` (higher wins; ties: newest). Unknown → `latest` |
| `priority` | 0 (low) … 2 (high) |
| `call` | the sender is in a phone / VoIP call |
| `playing` | a session of the sender plays (or buffers) |
| `cause` | `user`: a person started the current playback; `policy`: an automatic resume; `none` while not playing |
| `onsetAt` | sender wall clock (ms) of the last user-started playback; identifies it |
| `pausedAt` | > 0 while the sender holds sessions it paused for a peer and will resume (wall clock of that pause) |
| `app` | optional: app id of the playing session |

Rules (each device, about its own sessions):

1. A peer's new user-started playback (`playing` with `cause:"user"` and an
   `onsetAt` not seen before) pauses what plays here when this device yields:
   `latest` → when the peer's `onsetAt` ≥ ours; `priority` → when the peer's
   priority is higher, or equal and its `onsetAt` ≥ ours. Of two playbacks
   started at about the same time (messages crossing) only the older one yields.
2. A peer's call (`call` turning true) pauses what plays here in every mode
   except `off` (setting "pause for calls").
3. Automatic resumes (`cause:"policy"`) never make a peer yield.
4. When no peer plays or calls, sessions paused by rule 1 / 2 are resumed after
   3 s. Of several waiting devices the one with the latest `pausedAt` resumes
   first (ties: larger `deviceId`); the others keep waiting while it plays.
5. Pauses the engine did not cause (the user, the app, a PC's arbitration) are
   never undone; changing track while paused counts as a user decision; a pause
   or resume without effect within 4 s is not retried (a failed resume clears
   `pausedAt`).
6. The first `policy.peer` of a connection is a baseline: existing state, not a
   new playback. A peer that disconnects is not a reason to resume.

A PC's commands with `origin:"policy"` are attributed as such: a playback the
PC resumed is reported with `cause:"policy"`.
